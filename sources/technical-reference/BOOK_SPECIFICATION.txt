Nhiệm vụ của bạn là thiết kế và biên soạn giáo trình:

# 5. MANDATORY LESSON STRUCTURE

**Mỗi kiến thức phải có hội thoại phỏng vấn bằng tiếng Nhật.**

Không được chỉ viết lý thuyết.

Mỗi bài sử dụng cấu trúc:

### ① 面接質問 — Interview Question

Câu hỏi tiếng Nhật và bản dịch Việt.

### ② 質問の意図 — Interviewer Intention

Giải thích người phỏng vấn muốn đánh giá kỹ năng nào.

### ③ 技術知識 — Knowledge Foundation

Giải thích kiến thức cốt lõi.

Ưu tiên:
- Definition.
- Purpose.
- Practical usage.
- Important limitations.

### ④ 思考プロセス — Thinking Framework

Dạy quy trình suy nghĩ 2–4 bước.

Ví dụ:

Clarify → Analyze → Options → Explain.

### ⑤ 面接対話 — Interview Dialogue

Bắt buộc có ít nhất hai lượt hỏi–đáp.

Format:

面接官:
[Câu hỏi chính bằng tiếng Nhật]

応募者:
[Câu trả lời ngắn, đúng trọng tâm, 15–30 giây]

ベトナム語訳:
[Dịch]

面接官:
[Câu hỏi đào sâu]

応募者:
[Câu trả lời có lý do hoặc ví dụ]

ベトナム語訳:
[Dịch]

### ⑥ 模範回答 — Model Answers

Cung cấp hai cấp độ khi có giá trị học tập rõ ràng:

**Standard**
- Phù hợp N3–N2.
- Dễ ghi nhớ.
- Đúng kỹ thuật.

**Professional**
- Tiếng Nhật tự nhiên trong doanh nghiệp.
- Diễn đạt chính xác hơn.
- Không cố dùng Keigo phức tạp.

### ⑦ 深掘り質問 — Follow-up Questions

Tạo 1–3 câu hỏi liên quan đến câu trả lời trước.

Câu hỏi phải theo logic, không đổi chủ đề tùy tiện.

### ⑧ 語彙・文法 — Vocabulary & Grammar

Bao gồm:
- Từ tiếng Nhật.
- Kana.
- Nghĩa Việt.
- Cách sử dụng.
- Ví dụ ngắn.

### ⑨ 類似表現比較 — Expression Comparison

Khi phù hợp, so sánh:
- Từ gần nghĩa.
- Ngữ pháp gần nghĩa.
- Cách nói thông thường và lịch sự.
- Sắc thái trong phỏng vấn.

### ⑩ 会話練習 — Active Conversation Practice

Người học phải tự trả lời:

- Câu hỏi chính không nhìn mẫu.
- Câu hỏi đào sâu.
- Tình huống mới thay đổi dữ kiện.

### ⑪ 評価・改善 — Assessment & Improvement

Đánh giá câu trả lời, xác định lỗi và đề xuất sửa chữa.

# 6. INTERVIEW ANSWER STANDARDS

## 6.1. Conciseness

Main Answer:
- Mục tiêu 15–30 giây.
- Thường 2–4 câu Nhật.
- Nói trực tiếp ý chính.
- Không giải thích dài dòng.

Follow-up:
- Mục tiêu 10–25 giây.
- Trả lời vào vấn đề đang hỏi.

Project Overview:
- 30–60 giây.

Project Demo:
- 3–7 phút theo yêu cầu.

Không cắt thông tin quan trọng chỉ để đạt số giây.

## 6.2. Answer Frameworks

### Technical Definition

Definition → Purpose → Example.

### Technical Comparison

Difference → Usage → Example.

### Experience

Role → Action → Result.

### Problem Solving

Clarify → Analyze → Action → Report.

### Motivation

Answer → Reason → Career Goal.

### Technical Demo

User Action → Frontend → API → Business Logic → Database/IoT → Result.

Không áp dụng máy móc một công thức cho mọi câu hỏi.

## 6.3. Japanese Standards

- Dùng tiếng Nhật tự nhiên.
- Phù hợp mức độ N3–N2 hoặc cao hơn khi cần thiết.
- Đúng quan hệ xã hội.
- Giải thích kỹ thuật chính xác.
- Không sử dụng mẫu N1 chỉ để gây ấn tượng.
- Không trả lời theo cách dịch máy từ tiếng Việt.

# 8. KAIWA & MOCK INTERVIEW SYSTEM

Áp dụng chu trình:

**Understand → Imitate → Substitute → Respond → Roleplay → Retry**

### Understand

Phân tích câu hỏi, ngữ cảnh và ý định.

### Imitate

Luyện nói theo mẫu.

### Substitute

Thay công nghệ, tình huống hoặc dữ kiện.

### Respond

Trả lời mà không nhìn mẫu.

### Roleplay

AI đóng vai interviewer Nhật.

Yêu cầu:
- Hỏi từng câu.
- Đợi ứng viên trả lời.
- Không trả lời thay.
- Hỏi sâu dựa trên câu trả lời thực tế.
- Không hỏi dồn quá nhiều vấn đề.
- Có thể thay đổi mức độ khó.
- Đánh giá khi kết thúc.

### Retry

Người học trả lời lại sau feedback.

Chú trọng tiến bộ về:
- Logic.
- Độ chính xác kỹ thuật.
- Từ vựng tiếng Nhật.
- Độ tự nhiên.
- Khả năng phản hồi.

# 9. GRAMMAR & EXPRESSION CONTRAST

Mỗi bài học phải hỗ trợ so sánh những biểu đạt gần nghĩa khi có nội dung phù hợp.

So sánh theo:
- Core meaning.
- Nuance.
- Formality.
- Usage constraints.
- Spoken versus written Japanese.
- Interview suitability.
- Interchangeability.

Ví dụ:

確認します / 確認いたします

Giải thích:
- Cùng diễn đạt hành động xác nhận.
- 確認いたします trang trọng và mang sắc thái khiêm nhường hơn.
- Tùy người nghe và tình huống để lựa chọn.

Không mặc định cách nói trang trọng nhất luôn tốt nhất.

# 10. CHAPTER 12 — SMART FARM IOT MANAGEMENT SYSTEM

## 10.1. Project Purpose

Smart Farm IoT Management System là hệ thống quản lý vườn thông minh.

Hệ thống kết hợp:
- IoT devices.
- AWS IoT Core.
- Spring Boot Backend.
- PostgreSQL Database.
- React Frontend.

Mục đích:
- Theo dõi môi trường.
- Quản lý thiết bị và khu vực.
- Điều khiển tưới.
- Theo dõi cảnh báo.
- Quản lý lịch sử và quy trình tưới.

## 10.2. Technical Stack

### Firmware

- ESP32.
- C/C++.
- Arduino Framework.
- PlatformIO.

### Simulation

- Wokwi.

### Communication

- AWS IoT Core.
- MQTT.
- TLS.
- X.509 certificates.
- WSS / SigV4 ở kết nối backend đã mô tả.

### Backend

- Java 21.
- Spring Boot.
- Spring JDBC.
- AWS IoT Device SDK.
- Modular Monolith.

### Frontend

- React.
- TypeScript.
- Vite.
- Tailwind CSS.

### Database

- PostgreSQL 16.
- Flyway.

### Tools

- Python.
- Docker Compose.
- Git.
- Maven.

### Testing

- JUnit.
- Spring Boot Test.
- PostgreSQL integration tests.
- Playwright.

## 10.3. System Architecture

Telemetry:

Sensor → ESP32/Wokwi → AWS IoT Core → Spring Boot → PostgreSQL.

Web:

React ↔ REST API / Polling ↔ Spring Boot.

Control:

React → Backend → AWS IoT Core → ESP32 → Actuator.

Acknowledgement:

ESP32 → AWS IoT Core → Backend.

## 10.4. Architecture Explanation

Backend sử dụng Modular Monolith.

Các nhóm nghiệp vụ:
- Devices.
- Telemetry.
- Alerts.
- Automation.
- Control.
- Reporting.

Thiết bị giao tiếp bất đồng bộ qua MQTT.

Web giao tiếp với backend thông qua REST API.

Không mô tả hệ thống như microservices.

## 10.5. Telemetry

Mỗi bản tin có:
- device ID
- boot ID
- sequence
- measurement timestamp

Backend:
- Kiểm tra dữ liệu.
- Xử lý trùng lặp.
- Lưu lịch sử.
- Đánh giá cảnh báo.

## 10.6. Device Control

Phải giải thích rõ:

1. Backend lưu command ID và ý định.
2. Gửi lệnh MQTT.
3. Theo dõi kết quả publish.
4. Nhận ACK.
5. Kiểm tra trạng thái thiết bị được báo cáo.
6. Cập nhật kết quả tương ứng.

**Publish thành công không đồng nghĩa thiết bị đã thực hiện thành công.**

ACK không tự động chứng minh trạng thái vật lý nếu chưa có bằng chứng từ thiết bị hoặc cảm biến.

## 10.7. Irrigation

Bao gồm:
- Soil moisture rules.
- Allowed schedule.
- Timed control.
- Water conditions.
- Rain conditions.
- Valve feedback.
- Flow data.
- Irrigation sessions.
- Estimated water usage.

Không khẳng định hệ thống đã kiểm chứng điều khiển bơm/van nông nghiệp thật.

## 10.8. Project Status

Trạng thái thực tế theo mô tả:

- Backend và PostgreSQL chủ yếu chạy local.
- AWS IoT Core đã được sử dụng.
- Luồng ESP32/Wokwi–AWS–backend đã có bằng chứng chạy thử.
- Các tính năng nâng cao còn cần nghiệm thu.
- Chưa xác nhận production.
- Chưa xác nhận điều khiển bơm/van vật lý ngoài thực địa.

Phải phân biệt:

- Implemented.
- Tested.
- Production Verified.

Không được tự nâng mức độ hoàn thiện của dự án.

# 6. SMART FARM IOT VISUAL REQUIREMENTS

Chương 12 sử dụng Smart Farm IoT Management System làm Case Study.

Thiết kế các sơ đồ:

## 12.02 — System Architecture

Sensor → ESP32/Wokwi → AWS IoT Core → Spring Boot → PostgreSQL.

React ↔ REST API/Polling ↔ Spring Boot.

Command: Spring Boot → AWS IoT Core → ESP32 → Simulated Actuator.

## 12.04 — Telemetry Sequence

1. ESP32 đọc cảm biến.
2. Thiết bị publish telemetry.
3. AWS IoT Core tiếp nhận.
4. Backend nhận dữ liệu qua MQTT.
5. Backend validate.
6. Backend xử lý trùng lặp.
7. Backend lưu PostgreSQL.
8. Frontend lấy dữ liệu qua REST API.

## 12.05 — Command & ACK

1. User gửi yêu cầu điều khiển.
2. Backend lưu command intent và command ID.
3. Backend publish MQTT command.
4. Device nhận lệnh.
5. Device xử lý lệnh.
6. Device gửi ACK.
7. Backend nhận và đối chiếu ACK.
8. Backend cập nhật trạng thái.
9. Frontend hiển thị kết quả được xác minh.

Phân biệt rõ:

- Publish Result.
- Device ACK.
- Reported Device State.
- Verified Physical State (chỉ khi có dữ liệu thực tế hỗ trợ).

Không thể hiện ACK như bằng chứng duy nhất của điều khiển thành công.

## 12.06 — Irrigation Decision Flow

Minh họa:

- Soil moisture threshold.
- Allowed schedule.
- Rain conditions.
- Water availability.
- Valve/flow feedback.
- Timeout.
- Safety constraints.

Phân biệt logic được thiết kế với logic đã được kiểm thử.

## 12.07 — Error Handling

Minh họa:
- MQTT Offline.
- Missing ACK.
- Duplicate Telemetry.
- Command Timeout.
- Recovery / Retry / Escalation.

Chỉ thể hiện retry, timeout hoặc recovery là đã triển khai nếu có dữ liệu xác minh; nếu không, đánh dấu proposed design.

## 12.09 — Technical Demo Flow

User Action → React → REST API → Spring Boot → AWS IoT Core → ESP32 → ACK → PostgreSQL → Web Display.

Phải giải thích các bước và trạng thái kết quả, không được đơn giản hóa thành "Gửi lệnh thành công = Thiết bị hoạt động thành công".
